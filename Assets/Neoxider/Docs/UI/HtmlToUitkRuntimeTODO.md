# HTML → UI Toolkit: задачи

Приоритет: **runtime-преобразование во время работы приложения**, затем Editor-конвертация. Архитектура, ограничения и порядок этапов — в [плане](HtmlToUitkRuntimePlan.md). Ни один пункт ниже не считается выполненным только потому, что он записан.

## P0. База и контроль результата

- [ ] Сохранить независимые записи оригинала Velora и Unity в реальном времени; сверить разрешение, тему, масштаб, положения и действия.
- [ ] Зафиксировать различия цвета, контраста, размеров dashboard, шрифтов/иконок, фона и градиентов.
- [ ] Сверить и воспроизвести бегущую обводку, орбиты, эффекты ленты и метеоров: направление, траекторию, скорость, яркость и затухание; проверить hover и reduced motion.
- [ ] Устранить `No cameras rendering` в демо и проверить обычный Game View, не только снимок панели. Камера добавлена в сцену; повторная проверка Game View в Play Mode ещё не выполнена.
- [ ] После имеющихся изменений повторить графические Play Mode проверки и осмотреть четыре страницы и нижние секции при desktop/mobile размерах. Прогон Unity 6.3: 14/16 PASS; две pixel-проверки CTA FAIL, хотя на снимке Game View кнопка отображается синей. Разобрать чтение тестовой панели и повторить проверки до объявления готовности.
- [ ] Для двух CTA-проверок записать реальные значения пикселей, color space и форматы RenderTexture/readback; проверить линейное и sRGB-преобразование, а также ориентацию координат. Это гипотезы, а не установленная причина. Исправить подтверждённый дефект или сравнение без снижения порогов и повторить тесты.
- [ ] Разобраться с текущими переходами Velora: перенесённые страницы должны открываться в Unity; отдельная кнопка `Original` может открывать браузер явно.
- [ ] Зафиксировать фактическое состояние CLI, сборки и поставки: наличие только локального файла в `Tools/HtmlToUitk/bin` не доказывает работоспособность в UPM или на другом компьютере.

## P1. Runtime: основное направление

- [ ] Определить версии Unity/Player и форматы входа для первого работающего среза; сохранить текущие публичные API и сериализацию.
- [ ] Сначала проверить готовые WebView/CEF backend на целевых ОС и примерах Velora/Chicken Road; переиспользовать их через единый C# интерфейс и писать только недостающие платформенные адаптеры.
- [ ] Для gree проверить отдельный типизированный адаптер к `unity-webview` / `Gree.UnityWebView.WebViewObject`; отсутствие опционального пакета не должно ломать базовую сборку NeoxiderTools.
- [ ] Проверить platform filters поставляемых native DLL: в исследованном gree Windows x64 metadata включены Linux/macOS; не включать Windows binary в сборки других ОС.
- [ ] Выделить переиспользуемое HTML/CSS/IR-ядро без зависимости от `UnityEditor` и CLI; покрыть публичные контракты тестами.
- [ ] Проверить и исправить `singleDocument`, обработку `href`, ограничения script-атрибутов и существующий manifest градиентов; сохранить совместимость старых jobs и схем.
- [ ] Перед добавлением URL-настроек проверить текущую обработку версии job schema: Editor parser не должен молча терять неизвестные поля или переписывать новую версию как старую; добавить тесты миграции и round-trip.
- [ ] Создавать UI Toolkit `VisualElement` из runtime IR; проверить загрузку/замену/закрытие документа, фокус, формы и отмену.
- [ ] Переиспользовать текущие root connection, disposable action bindings, router и responsive controller без дублирования обработчиков и владельцев состояния.
- [ ] Поддержать текст, шрифты, изображения, layout, responsive, кнопки, ссылки, CSS-переменные, поддерживаемые переходы и анимации.
- [ ] Ввести интерфейс JS adapter и сравнить проверяемые версии движков на Mono, IL2CPP и целевых платформах, включая лицензии и размер.
- [ ] Провести spike по [обзору открытых решений](HtmlToUitkOpenSourceResearch.md): ReactUnity, OneJS, DOM/JS и подходящий web backend; отдельно доказать native UITK-проекцию и поведение выбранного backend, не смешивая эти результаты.
- [ ] Добавить выбор `Auto` / native / web sandbox: неподдерживаемые JS, CSS, анимации и Canvas либо работают в подходящем backend, либо явно отражаются как неперенесённые; никаких незаметно пропавших эффектов.
- [ ] Проверить динамические ошибки и безопасную смену backend: автоматический повтор не должен повторять формы, запросы с побочным эффектом или игровой раунд.
- [ ] Добавить единые типизированные настройки и C# API для JavaScript, анимаций/переходов, взаимодействий, ресурсов, аудио/видео, Canvas/WebGL, режима backend и области обхода; отразить их и в редакторских вкладках.
- [ ] Задать и проверить semantics отключения/повторного включения: lifecycle JS, CSS/UITK-анимации и `prefers-reduced-motion`; не отключать произвольный `requestAnimationFrame` так, чтобы молча остановить игровую логику.
- [ ] Для web backend проверить изоляцию на каждой платформе, ограниченный мост к Unity, ввод, прозрачность/перекрытие и стоимость кадров. Не считать сам JS-интерпретатор изолированным процессом.
- [ ] Реализовать DOM/CSSOM и мост событий, таймеров, `requestAnimationFrame`, модулей и ресурсов с корректным lifecycle и порядком обработки.
- [ ] Проверить сначала vanilla JS, затем React: реальное изменение состояния, перестроение DOM, CSS-in-JS, ввод и обновление UI без ручного переписывания примера.
- [ ] Разделить и проверить Canvas 2D, WebGL/Pixi и Spine как отдельные возможности; не выдавать статичный снимок за рабочую игру.
- [ ] Для `D:\AI\chicken-road` составить перечень требуемых JS/API, ресурсов и визуальных эффектов; проверить меню, историю, игру и анимации по сценариям с тестовым backend без реальных денег и без изменения оригинала.
- [ ] Реализовать отмену, лимиты времени/памяти, явные host capabilities и diagnostics для неподдержанного поведения.

## P1. Ссылки и выбор области сайта

- [ ] Добавить режимы: текущая страница; связанные страницы того же домена; все связанные страницы в заданных пределах.
- [ ] Сделать режим одной страницы значением по умолчанию. Анимации, обработка кнопок и нужные ресурсы включать по умолчанию там, где поддержка подтверждена.
- [ ] Определять домен с учётом public suffix и поддоменов; дать опцию точного хоста. IP/localhost обрабатывать отдельно.
- [ ] Корректно обрабатывать relative URL, query, fragment, коды ошибок, redirects, циклы, дубликаты и отмену; после каждого redirect заново проверять область обхода.
- [ ] Ввести видимые пределы глубины/числа страниц/размеров, timeout и параллелизм; показывать пропуски и причину остановки.
- [ ] Навигировать между успешно перенесёнными страницами внутри Unity; проверить историю, Back и якоря. Внешний переход разрешать явно, а не вместо локальной страницы.

## P1. Производительность и надёжность

- [ ] Кэшировать исходники, ресурсы, разбор и неизменяемые части IR по версиям/хешам; ограничивать объём и проверять инвалидирование.
- [ ] Группировать DOM-изменения и применять корректный diff вместо перестройки всей страницы каждый кадр; сохранять состояние элементов.
- [ ] Ограничивать время работы скриптов и очередей; не скрывать пропущенные события, ошибки или некорректный порядок вызовов.
- [ ] Профилировать 1/100/1000+ элементов, длинную страницу, resize, навигацию и повторное открытие: p50/p95/p99 frame time, JS/layout/render CPU, GC, память и draw calls.
- [ ] Заранее задать измеримые бюджеты по контрольным устройствам; сравнить до/после и проверить отсутствие утечек. Проверить runtime на реальном Player, включая AOT/IL2CPP.

## P2. Конвертация в редакторе и UX

- [ ] Построить Editor export поверх того же ядра: UXML, USS, ресурсы и metadata; обеспечить детерминированность и обратную совместимость job-файлов.
- [ ] Разделить окно на понятный стартовый экран сайта, отдельные настройки и результаты/диагностику; исправить переполненную верхнюю панель.
- [ ] Обеспечить сценарий по умолчанию: указать URL или локальную папку → обработать одну страницу с работающими поддерживаемыми элементами.
- [ ] Добавить явные настройки области обхода, анимаций, кнопок, ресурсов и лимитов, с включёнными поддерживаемыми возможностями по умолчанию.
- [ ] Сделать готовый runner доступным в заявленных способах установки или объяснять конкретное действие по установке; не зависеть от временного пути агента.
- [ ] Документировать оба C# API и Editor workflow на русском и английском, лицензии и реальные ограничения/диагностику.

## Приёмочные проверки

- [ ] Тесты ядра: URL/локальные пути, загрузка, отмена, redirect, scope, дубликаты, хеши, resource limits и корректность diagnostics.
- [ ] Runtime-тесты: DOM/стили/события/async, таймеры, layout, динамические изменения, локальная навигация, фокус, ввод и освобождение ресурсов.
- [ ] Один и тот же тестовый контент через runtime и Editor должен давать согласованное поведение; старые fixture/job и публичные API остаются рабочими.
- [ ] Реальные браузер и Unity сравниваются по зафиксированным размерам, состояниям и временным точкам; расхождения кадров и поведения перечислены, а не скрыты усреднённой оценкой.
- [ ] Velora и Chicken Road проходят конкретные сценарии пользователя; неподдержанные Canvas/JS/Spine/веб-API остаются честно отмеченными до подтверждённой реализации.
- [ ] Подтвердить Player-сборки и измеренные бюджеты производительности. Обновить документацию и очистить только проверенные собственные временные артефакты.
