# HTML → UI Toolkit: план runtime-first

Статус: **план, функциональность ниже ещё не реализована**. Список конкретных задач и критериев готовности: [HtmlToUitkRuntimeTODO.md](HtmlToUitkRuntimeTODO.md). Основная документация модуля остаётся в [HtmlToUitk.md](HtmlToUitk.md).

## Цель и приоритеты

1. **Основной путь — runtime.** Приложение Unity получает HTML, CSS, JavaScript и ресурсы из указанного URL или локального сайта; во время работы создаёт и обновляет интерфейс, а также обрабатывает взаимодействия и изменения состояния. Поддерживаемые функции преобразуются в нативный UI Toolkit; когда для сохранения поведения нужен браузерный движок, допускается изолированный web-backend внутри Unity. Цель — максимально близкое к оригиналу отображение и поведение по умолчанию, включая адаптивность, кнопки и анимации.
2. **Второй путь — Editor.** Тот же исходный сайт можно обработать до Play Mode и экспортировать UXML/USS, ресурсы и данные поведения. Оба пути должны использовать общие контракты и промежуточное представление, чтобы исправления парсинга и преобразования не расходились.

Это целевой уровень, а не обещание, что произвольный сайт уже поддерживается. Нельзя считать статичный скриншот или неподвижную копию успешным переносом интерактивной страницы. Неподдержанные возможности необходимо обнаруживать и показывать вместе с их влиянием на результат.

## Отправная точка

- Текущий `Neo.HtmlToUitk.Runtime` отображает подготовленные UI Toolkit-ресурсы и использует metadata для навигации, анимаций и адаптивности. Существующий CLI конвертирует поддерживаемое подмножество локальных HTML/CSS в редакторские ресурсы. Автоматического обхода сайта по URL и выполнения произвольного JavaScript в нём сейчас нет.
- Текущее демо Velora — ручная адаптация исходника с последующей конвертацией, а не доказательство автоматического переноса сайта. Часть пунктов шапки сейчас открывает оригинал в браузере. Проверка после последних исправлений сцены ещё не завершена.
- `D:\AI\chicken-road` — отдельный пример пользователя; исходный проект менять нельзя. Его страница создаётся JavaScript/React, игровая часть использует Pixi и данные Spine. Самого чтения статического HTML недостаточно для интерактивного результата.
- Текущий validator отклоняет обычные `href` и script-атрибуты; схема заявляет `singleDocument`, но фактическая сборка отдельных документов требует отдельной проверки и исправления. Manifest сгенерированных ресурсов сейчас рассчитан на gradient PNG, а не произвольные изображения и шрифты. Эти контракты нужно расширять совместимо, не считая существующие схемы готовым site-import.
- Unity позволяет создавать UI Toolkit-дерево через C#, но [не создаёт `VisualTreeAsset` из сырой строки UXML в runtime](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/UIElements.VisualTreeAsset.html). Поэтому в Player общий IR должен строить и обновлять живые `VisualElement`; UXML/USS экспортируется для Editor-пути. Unity также [поддерживает в USS подмножество CSS](https://docs.unity3d.com/6000.0/Documentation/Manual/ui-systems/introduction-ui-toolkit.html).

## Архитектура

Предлагаемые ниже названия контрактов условны: они описывают границы будущих модулей, а не существующий API.

```text
URL / локальная папка / готовые данные
  → ограниченная загрузка страниц и ресурсов
  → HTML DOM + CSSOM + очередь JavaScript-событий
  → общее промежуточное представление интерфейса и поведения
  ├─ runtime native: изменения → живые VisualElement / ресурсы / эффекты
  ├─ runtime web: страница исполняется в изолированном backend внутри Unity
  └─ editor: экспорт UXML / USS / ресурсов / metadata
```

### Слои

1. **Источник и загрузчик.** Контракты для локальных файлов, HTTP(S), кэша и тестовых источников. Отдельные лимиты на размер, число запросов, параллелизм, время ожидания и редиректы; отмена корректно останавливает незавершённую загрузку.
2. **Общее ядро.** Разбор HTML/CSS, DOM, стиль, ресурсные ссылки, diagnostics и сериализуемое промежуточное представление — без `UnityEditor` и без обязательного CLI. Проверить, что можно вынести и переиспользовать из `Tools/HtmlToUitk/src/HtmlToUitk.Core` и `HtmlToUitk.Convert`, не ломая текущие проекты и схемы.
3. **Runtime-проекция.** Адаптер создаёт нативные `VisualElement` и применяет стили; сохраняет идентичность узлов между изменениями, фокус, ввод, состояние форм и подписки. Переиспользовать существующие `UitkRootConnection`, `UitkActionBindings`, `UitkRouter` и `BreakpointController` там, где их контракты подходят; не создавать второй конкурирующий owner событий и навигации. Несколько независимых документов не должны делить состояние или блокировать друг друга.
4. **JavaScript и веб-окружение.** Изолированный интерфейс движка JS и ограниченные мосты DOM/CSSOM, событий, таймеров, `requestAnimationFrame`, модулей, ресурсов и сетевых запросов. JS-движок сам по себе не предоставляет браузерный DOM, CSS layout, Canvas, WebGL или API фреймворков: каждый слой необходимо отдельно реализовать и проверить. Для React проверить создание и изменение DOM, обработчики, состояние и обновление стилей, включая CSS-in-JS.
5. **Графика и интеграции.** Canvas/WebGL, SVG, видео, фильтры, шрифты, Pixi и Spine — отдельные capability/adapters, подключаемые по необходимости. Например, Canvas/WebGL может потребовать отдельного render backend и проекции результата в Unity. Обычная DOM-снимок не сохраняет интерактивную игру. Использование [spine-unity](https://esotericsoftware.com/spine-unity) требует проверки версии и условий лицензии; не включать его незаметно в обязательные зависимости.
6. **Editor-адаптер.** Общие input/IR/diagnostics и отдельный экспортёр файлов. Редакторские API не должны попадать в Player. Генерация и повторный импорт должны быть детерминированными и не перезаписывать пользовательские ресурсы без явного выбора.

Выбор движка JS и графического backend — отдельный проверяемый spike, не уже принятое решение. [Обзор открытых проектов](HtmlToUitkOpenSourceResearch.md) сравнивает ReactUnity/OneJS, DOM/JS-инструменты и встраиваемые web backends. Сравнить как минимум управляемый интерпретатор и нативный вариант по поддержке нужных JS/Web API, расходам, лицензиям и сборкам Mono/IL2CPP/Web. Например, [Jint](https://github.com/sebastienros/jint) является кандидатом, но совместимость конкретной версии с Unity и нужными браузерными API необходимо проверить; использовать неподтверждённую preview-версию как готовую зависимость нельзя. [IL2CPP имеет AOT-ограничения](https://docs.unity3d.com/6000.0/Documentation/Manual/scripting-restrictions.html).

Проверять отдельно два результата: **native UI Toolkit** с доступными Unity-элементами и **web backend** для браузерных функций. Для уменьшения объёма ручного переноса первым практическим spike проверить готовый web backend на оригинальных страницах и по возможности переиспользовать его. Встроенный web renderer исполняет страницу внутри Unity, но сам по себе не является преобразованием DOM/JS в нативные UXML или C# и должен быть обозначен именно как отдельный backend. В режиме `Auto` выбирать нативный путь, когда необходимые возможности подтверждены, либо совместимый web backend, когда он лучше сохраняет поведение; показывать выбор и неподдержанные возможности. Если подходящего backend нет, выдавать понятный результат с ограничениями, не скрывая исчезнувшие кнопки или эффекты. Явный выбор backend остаётся доступен разработчику.

Анализ до запуска не может заранее обнаружить все вызовы динамического JS. Поэтому backend выбирается с учётом известных требований и платформы, а возникшие во время исполнения пробелы отражаются в diagnostics. Автоматический переход к другому backend не должен повторно выполнять действия с побочными эффектами, повторно отправлять формы или создавать игровой раунд; момент и семантику перезапуска нужно определить и протестировать отдельно.

Кроссплатформенный `IWebRuntimeBackend` должен объединять разные существующие реализации, а не предполагать один одинаковый системный движок на всех ОС. В качестве кандидатов проверить Android WebView, iOS/macOS WKWebView и Windows WebView2 через [gree/unity-webview](https://github.com/gree/unity-webview); для Linux и сравнения desktop — [UnityWebBrowser/CEF](https://github.com/Voltstro-Studios/UnityWebBrowser). Upstream уже описывает несколько платформ для gree/unity-webview. Его README говорит о сборке Windows DLL, но в проверенном UPM-снимке [готовая x64 DLL присутствует](https://github.com/gree/unity-webview/blob/950cfbac14dbbf72e87548e77ef11ecc8843988e/dist/package/Assets/Plugins/Windows/x64/WebView.dll): до применения проверить её происхождение, совместимость и стоимость вывода по кадрам. UnityWebBrowser 2.2.8 [официально не поддерживает IL2CPP](https://github.com/Voltstro-Studios/UnityWebBrowser/blob/2.2.8/docs/articles/user/setup.md#platform-support), а его Linux backend [отключает CEF sandbox](https://github.com/Voltstro-Studios/UnityWebBrowser/blob/2.2.8/src/UnityWebBrowser.Engine.Cef/Main/Core/CefEngineControlsManager.cs); поэтому он не годится как единственный изолированный backend для всех Player. Поддержка наших версий Unity, IL2CPP, Canvas/Pixi/Spine, прозрачности и ввода **не подтверждена**, пока не пройдены собственные Player-тесты на каждой платформе. Исходную библиотеку переносить или форкать только если адаптера и существующего API недостаточно.

Гибридное отображение отдельных сложных областей допустимо исследовать отдельно: синхронизация DOM, стилей, перекрытия, координат и событий между разными движками не считается решённой автоматически. До доказательства корректного hybrid предпочтительнее сохранить связанные JS/CSS/Canvas в одном web-контексте, чем разорвать их и заявить идентичное поведение.

### Настройки и C# API

Для runtime и Editor нужны одинаковые типизированные настройки: `Auto/native/web backend`, область и лимиты обхода, JavaScript, CSS/UITK-анимации и переходы, обработка взаимодействий и ссылок, изображения/шрифты, аудио/видео и Canvas/WebGL. Возможности, которые backend поддерживает, по умолчанию включены; разработчик может отключить ненужное. В окне настройки разделены по вкладкам, а код получает эквивалентный явный API без обязательной scene/NoCode-связки. Названия будущих классов не фиксируются до API spike.

Минимальный контракт API: настройки передаются при асинхронном открытии URL или локального источника; результат возвращает сессию с текущим backend, состоянием загрузки и diagnostics. Сессия предоставляет переход, Back, изменение viewport, отмену и освобождение ресурсов. Изменение настроек во время работы должно либо применяться атомарно, либо возвращать явное требование перезапуска документа; повторный вызов не создаёт дублирующих обработчиков. Для внешних событий и мостов к игре используются типизированные callbacks, а не обязательные цепочки `UnityEvent`.

Применение настроек должно иметь определённую семантику: отключение JS отменяет принадлежащие странице обработчики и таймеры; повторное включение выполняет документированный reload/reinitialization, а не оставляет полуживое состояние. Отключение анимаций останавливает поддерживаемые CSS/UITK-эффекты и учитывает `prefers-reduced-motion`. Произвольную игровую анимацию внутри JavaScript нельзя надёжно отличить от игровой логики только по использованию `requestAnimationFrame`; её отключение требует поддержки сайта/backend и отражается в diagnostics, а не молча ломает игру. При изменении настроек тестировать отмену операций, повторное включение и освобождение ресурсов.

## Обход страниц и поведение ссылок

Один механизм действует в runtime и Editor. По умолчанию выбирается **только текущая страница**; анимации, кнопки, стили и необходимые ресурсы включены, если поддерживаются. Параметры доступны отдельно.

| Режим | Область |
|---|---|
| Текущая страница | Загрузить указанную страницу и необходимые ей ресурсы, не обходить ссылки на другие страницы. |
| Связанные страницы домена | Обходить связанные страницы в заданной области домена; по умолчанию учитывать поддомены этого зарегистрированного домена, а для IP/localhost — точный хост. Опция точного хоста остаётся доступной. |
| Все связанные страницы | Разрешить обход ссылок и на другие домены в заданных пределах. Это обход графа ссылок, а не обещание скачать бесконечный Интернет. |

Определение зарегистрированного домена требует проверенного списка public suffix; простое сравнение двух последних частей имени недостаточно. Нормализовать относительные URL, порты и кодирование; сохранять значимые query-параметры, отделять якорь от идентичности документа, не зацикливаться и повторно проверять область после каждого redirect. Лимиты страниц и глубины настраиваемые и видимые; при достижении лимита результат и пропущенные ссылки перечисляются в отчёте. Для локального сайта нормализовать пути и не выходить за выбранную корневую папку.

Ссылки на **успешно перенесённые** страницы ведут к локальной runtime-странице; переходы, история, якоря и Back должны работать внутри приложения. Неперенесённая ссылка не должна молча выдавать себя за локальную: показывать её назначение и результат выбора режима. Внешний браузер допустим как явно выбранное пользователем действие, например кнопка `Original`, а не скрытая подмена локального перехода. Не запускать автоматически действия форм, изменение серверного состояния или произвольные скриптовые вызовы при обходе.

## Оптимизация — обязательная часть дизайна

- Разбирать исходники и загружать ресурсы асинхронно там, где это поддерживает платформа; Unity-объекты изменять на главном потоке. Ограничивать параллелизм и объём очередей. Обработать платформы без доступных managed threads отдельно.
- Кэшировать исходники по версии/хешу, результаты разбора, неизменяемые части IR, изображения, шрифты и стили; учитывать изменившиеся зависимости, освобождать ресурсы по lifecycle и ограничивать размер кэша. Сетевые запросы к одному ресурсу объединять.
- Группировать DOM-изменения и применять минимально необходимый diff с устойчивыми ID узлов; корректно инвалидировать наследуемые стили и селекторы, когда изменение влияет на другие элементы. Не пересоздавать всё дерево каждый кадр и не перекладывать постоянные данные через C#↔JS на каждом обновлении.
- Планировать таймеры, анимации и ресурсы по кадрам; ограничивать ресурсы и время исполнения скриптов, выдавать диагностическую ошибку при превышении. Не терять события и не менять порядок задач/микрозадач молча ради FPS. Экспериментально проверить возможность прерывания JS и стоимость перехода между движками.
- Учитывать виртуализацию длинных списков, предпочтение трансформаций вместо постоянного перерасчёта layout, `usageHints`, повторное использование выделений и удаление обработчиков при закрытии документа. Графические эффекты должны иметь измеряемую стоимость и опцию качества.
- На фиксированных машинах измерять первый показ, загрузку страницы и ресурсов, FPS и frame time p50/p95/p99, время JS/layout/render, GC allocations, managed/native/GPU memory, draw calls и утечки после повторного открытия. Проверить масштабы 1/100/1000+ интерактивных элементов, длинные списки, resize и несколько параллельных документов. Цели и пороги фиксируются для каждой контрольной сцены и устройства **до** оптимизации; результаты браузера и Unity приводятся с разрешением и железом.

## Этапы реализации

1. **База и сравнение.** Зафиксировать текущие возможности, снять реальные видео оригинала и Unity в сопоставимых условиях, записать расхождения и минимальные воспроизводимые тесты. Исправить ошибку камеры и проблемы уже существующего демо.
2. **Runtime spike готового web backend.** В отдельном тестовом проекте проверить штатные платформенные реализации на Velora и локальном Chicken Road: исполнение исходных JS/CSS, видео движения, ввод и стоимость Player. Сохранить неудачи и выбрать минимальный адаптер без переписывания браузера.
3. **Нативный runtime и живое поведение.** Локальная HTML/CSS-страница → живые элементы в Player без CLI; затем проверенный JS adapter и DOM/CSSOM/event/timer bridge. Доказать на небольших версиях vanilla JS, затем React со state, событиями и динамическими стилями. Добавить инкрементальные обновления и профилирование.
4. **URL и несколько страниц.** Три режима обхода, локальная навигация и отчет о покрытии. Проверять на локальном тестовом сервере, а не полагаться исключительно на доступность внешнего сайта.
5. **Анимации и сложная графика.** Воспроизведение переходов, keyframes, градиентов, визуальных эффектов, hover/focus и reduced motion нативно либо в совместимом web backend; затем проверяемые адаптеры Canvas/Pixi/Spine и иных сложных функций.
6. **Второй режим — Editor export.** Экспорт из общего IR в UXML/USS и совместимые runtime-данные; настройки и UI в отдельных вкладках, по умолчанию сценарий ввода одного URL/пути и преобразования текущей страницы. Сохранить старые job-файлы и API.
7. **Проверка Player и документация.** Полные сценарии Velora и Chicken Road, build-пробы Mono и IL2CPP на целевых версиях Unity, профилирование, руководство на русском и английском и лицензии зависимостей.

Этапы 3 и 5 зависят от результатов spike. Если выбранный backend не проходит платформенные или функциональные проверки, результат помечается неподдержанным и ищется другой backend; нельзя подменять его неподвижным макетом и считать задачу выполненной.

## Приёмка на примерах пользователя

**Velora UI:** сравнить [оригинал](https://velora.colorlib.com/templates/saas) и Unity при одинаковом размере окна, масштабе, теме и времени. Проверить светлую/тёмную палитры, градиенты и контраст; размеры dashboard, текст, шрифты и иконки; движение световой обводки, орбит, ленты отзывов и метеоров, их траекторию, цвет и затухание. Проверить переходы шапки, формы, кнопки, scroll, адаптивность и reduced motion. Оригинал и Unity записать в реальном времени, затем сопоставить кадры и движения; не скрывать отсутствие эффекта. Убрать из Game View `No cameras rendering` и подтвердить это именно реальным Game View, а не только снимком `RenderTexture`.

**Chicken Road:** взять локальный `D:\AI\chicken-road` только как исходный пример. Проверить не только наличие DOM, но и видимый игровой Canvas/Pixi, загрузку атласов и Spine, анимации и ввод. Меню, история и игровые состояния находятся внутри SPA и не сводятся к обходу ссылок: нужны воспроизводимые сценарии действий. Для игровых действий и сетевого поведения использовать контролируемый тестовый backend/заглушку и согласованный сценарий, без операций с реальными деньгами. Проверить настройки сложности, ставку, шаг, завершение раунда, баланс и историю; не заявлять совпадение вероятностей или RNG с онлайн-оригиналом. Результат PASS возможен только после проверки реального поведения и соответствующих разрешённых ресурсов. Фактические неподдержанные возможности перечислять в отчёте.

## Границы и совместимость

Оба режима должны работать без обязательного NoCode-слоя и с тестируемым C# API. Сохранять существующие сериализованные поля, сцены и API; миграции фиксировать явно. Песочница должна иметь проверенные границы на каждой платформе: отдельный JS-интерпретатор сам по себе не является защитной границей процесса. Не включать неограниченный доступ исполняемого JS к CLR, файловой системе или сети по умолчанию; перечислить разрешённые host capabilities и лимиты, отделить доверенный локальный контент от загруженного извне. Источники, лицензии и версии сторонних движков и ресурсов фиксируются до их поставки. Временные файлы и копии примеров должны быть отдельными от пользовательских проектов и удаляться только после проверки их принадлежности задаче.
