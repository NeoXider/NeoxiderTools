# HTML → UI Toolkit: runtime-first roadmap

This is a **plan**, not a claim that the features are already implemented. The primary module guide is [HtmlToUitk.md](HtmlToUitk.md); the detailed Russian [plan](../../Docs/UI/HtmlToUitkRuntimePlan.md), [task list](../../Docs/UI/HtmlToUitkRuntimeTODO.md) and [open-source research](../../Docs/UI/HtmlToUitkOpenSourceResearch.md) are the authoritative work items.

The first priority is to load HTML, CSS, JavaScript and resources at runtime and project a live, interactive interface into Unity. The second path exports UXML, USS and behavior metadata in the Editor using the same intermediate representation. Unity does not create a `VisualTreeAsset` from raw UXML at runtime, so the Player path must construct and update `VisualElement` trees directly. Full visual and behavioral parity is the goal; unsupported browser APIs, JavaScript, Canvas, WebGL and third-party animation runtimes must be reported rather than represented as complete.

The proposed layers are source/resource loading, shared HTML/CSS/DOM and style processing, runtime UI projection, an optional JavaScript engine and Web API bridge, graphics adapters, and an Editor exporter. First evaluate existing WebView/CEF integrations on the user's examples to minimize custom work. A separate isolated web backend may run unsupported browser features within Unity; an automatic mode should select a verified backend and report the choice instead of silently dropping effects. A web renderer is a separate backend, not a conversion to native UXML/C#. Engine choices, isolation and Mono/IL2CPP/platform support require measured proof and license review. The existing converter supports a subset of local HTML/CSS and generated runtime metadata; it does not yet crawl sites or run arbitrary JavaScript.

Site import must offer **current page** by default, **linked pages in the same domain**, and **all linked domains** with visible configurable limits. Successfully imported pages navigate inside the application; explicit external links remain distinguishable. Supported JavaScript, animations, interactions and resources should be enabled by default and configurable through both the Editor and typed C# API. Disabling animation must not silently break game logic driven by arbitrary `requestAnimationFrame` callbacks.

Performance is a requirement: cache parsing and assets, batch changes, update only affected UI while correctly invalidating dependent styles, bound script work, cancel unused requests and release subscriptions/resources. Record frame-time percentiles, JS/layout/render time, allocations, memory and load time on representative devices and 1/100/1000+ interactive elements. Preserve old APIs and keep the runtime core independent of Editor and NoCode workflows.

Acceptance uses the original [Velora UI SaaS](https://velora.colorlib.com/templates/saas) and the user's local Chicken Road project, with browser/Unity recordings at matching viewport and state. Test color, layout, moving borders, meteors, orbit and marquee animations, navigation, forms, responsiveness, React state, and the actual Canvas/Pixi/Spine game behavior. A static snapshot alone is not a pass. The scene's `No cameras rendering` overlay must also be checked in the actual Unity Game View.
