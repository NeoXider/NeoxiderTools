## Entry points and isolation contract

Build entrypoint: `Neo.Tests.Network.Integration.Audit20261023TestPlayNetworkPlayerBuild.Build`, invoked by the verification operator in an **isolated validation project after every writer finishes**. Required build CLI suffixes: `-neoNetworkMatrixBuildRunId`, `-neoNetworkMatrixBuildSnapshot`, `-neoNetworkMatrixBuildOutput`. Output must be new. It builds three `StandaloneWindows64` players sequentially with `Development | IncludeTestAssemblies | StrictMode`. Build receipt must pass before launch; compilation/Weaver or build failure cannot count as network acceptance.

Runtime bootstrap: `Audit20261023TestPlayNetworkPeerDriver` responds only to exact `-neoNetworkMatrix`. The launcher supplies correlated RunId/Snapshot/Peer/Root/Company/Product/PersistentDataPath/Port/PhaseTimeout/OverallTimeout options. Roles are exactly `server`, `client-a`, `client-b`. Runtime symbol guards and assembly constraints keep these entrypoints out of ordinary production players. No new production public API or serialized migration was introduced.

The run ID is a unique32-hex value baked into company `NeoQA_Network_<run ID>` before building. Products are `NetworkMatrix_server`, `NetworkMatrix_client-a`, `NetworkMatrix_client-b`, giving three distinct actual Windows persistentDataPath and `HKCU\Software\<company>\<product>` PlayerPrefs namespaces. The launcher requires their prior absence; each player validates actual identity/path before scenario setup. The persistentDataPath CLI value is an assertion, **not an invented Unity path override**.

Before any provider load/write, each player emits environment/PID/transport/store locations. It installs an existing `FileSaveProvider` with explicit `FileSaveProviderOptions.PersistenceRoot=<artifact root>/<role>/save`, round-trips and deletes only its run-specific sentinel, and checks provider identity at phase boundaries. Original Counter/Selector saves, original-wallet persistence and RPG load/autosave are explicitly disabled. The NI7-02 additional wallet and NI19 Counter fixture identities enable persistence with their own unique run-owned keys in that isolated provider. No PlayerPrefs call occurs in the scenarios. The registry probe reads key/value **names**, not saved values, and removes nothing. Build identities also isolate any implicit Unity state.

The launcher retains only Process objects it started, refuses existing artifact roots/listeners and never enumerates/terminates foreign Unity processes. It uses a named port mutex and a TCP availability reservation; an external bind race is a failed owned run, not grounds for taking over the listener. Normal cleanup requires zero exit codes and one successful cleanup/result per role. Forced owned-process termination is recorded as cleanup debt. All artifacts and owned persistence are retained; no recursive deletion is performed by the launcher.

`<role>/events.jsonl` schema1 includes run/SHA/role/PID, server-side sender connection, epoch, step/case, pass/failure/detail, realtime, environment and actual state. State includes net/player IDs, ownership/Start completion, Counter, full Selector active/excluded arrays, Money, RPG HP/max/custom resource, property/reactive values, target/sibling child states, polling reads, exact Unicode lease payload and named event-value arrays. Array lengths are the event counts. The server receives the client's observed state in a distinct `remote-receiver` record; the launcher compares it with that client's `receiver` record by step/epoch/case and checks key payloads independently. Sending a message or keeping a process alive is insufficient.
