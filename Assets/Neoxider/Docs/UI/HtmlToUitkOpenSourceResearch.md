# HTML/CSS/JS → Unity: обзор готовых решений

Проверка первичных источников: 27 октября 2026. Это список кандидатов для экспериментов, **не результаты интеграции или гарантия совместимости** с NeoxiderTools. Приоритет и критерии приёмки находятся в [runtime-плане](HtmlToUitkRuntimePlan.md) и [TODO](HtmlToUitkRuntimeTODO.md).

### Практическая гипотеза для кроссплатформенности

`gree/unity-webview` — не только Android: его текущий README описывает Android/iOS, macOS, Windows и отдельный WebGL-путь. На мобильных устройствах используются native WebView/WKWebView, а на Windows — WebView2; это разные системные реализации под общей обёрткой. В текущем исходнике Linux-путь обозначен как неподдержанный. UnityWebBrowser/CEF имеет Linux-реализацию, но в версии 2.2.8 она принудительно запускается без CEF sandbox; требуется иное решение или доказанное исправление, прежде чем рассматривать её для изолированного исполнения. Это **заявления и кандидаты upstream**, а не результаты тестирования нашего Player.

Предлагаемый минимум собственного кода — единый typed API и независимые адаптеры существующих backend: загрузка URL/локального сайта, навигация и история, управление viewport, ввод и фокус, конфигурация JS/анимаций/ресурсов, lifetime и diagnostics. Сначала использовать существующий публичный API библиотек; форк и платформенный код добавлять лишь для подтверждённого пробела. На Windows отдельно измерить стоимость текстурного вывода, а на Android/iOS — ограничения native overlay и взаимодействие с UI Toolkit. Для WebGL проверить режим host browser и ограничения встраивания отдельно.

У gree уже есть `LoadURL`, `LoadHTML`, `EvaluateJS`, размер, видимость и callbacks, поэтому первый тест можно строить на штатной поверхности. В Windows-обёртке текстура приватна, а отрисовка и пересылка ввода выполняются через `OnGUI`. Если потребуется именно встраивание в UI Toolkit, может понадобиться небольшое расширение C#-обёртки с явным владением текстурой и вводом; его надо проверить на отсутствие двойной отрисовки и повторных событий. Native renderer ради этого заранее переписывать не нужно.

В локально сверенном с pinned Git tree UPM snapshot уже есть `unity-webview.asmdef` и публичный `Gree.UnityWebView.WebViewObject`. Это даёт основу для типизированного отдельного адаптера без обязательной рефлексии. Бинарная совместимость Windows DLL с этой версией обёртки пока не проверена: загрузка DLL и ABI-inspection были остановлены из-за нехватки свободного commit; локальный snapshot в этой работе неполон и не является установочным пакетом.

В [Windows source gree](https://github.com/gree/unity-webview/blob/950cfbac14dbbf72e87548e77ef11ecc8843988e/plugins/Windows/WebViewPlugin.cpp) описаны разные пути захвата: D3D11 с использованием устройства Unity и GPU-копированием, отдельный D3D11/readback и fallback `CapturePreview`. README и source расходятся в деталях частоты обновления, поэтому результат следует фиксировать по реальной DLL, выбранному API и измеренным кадрам, а не по одному описанию. Само наличие быстрого пути в исходнике не доказывает, что он работает в поставленной DLL или на конкретном устройстве.

Перед кроссплатформенной поставкой проверить [настройки импорта Windows x64 DLL](https://github.com/gree/unity-webview/blob/950cfbac14dbbf72e87548e77ef11ecc8843988e/dist/package/Assets/Plugins/Windows/x64/WebView.dll.meta): в выбранном снимке явно включены Linux64 и OSXUniversal. Это не является реализацией WebView для этих систем; platform filters необходимо проверить и исправить, чтобы Windows DLL не попадала в чужие Player-сборки.

## Загрузка сайтов и проверка результата

- [Crawlee](https://github.com/apify/crawlee) — Apache-2.0, Node.js crawler. Уже содержит стратегии [same-hostname, same-domain и all](https://github.com/apify/crawlee/blob/master/CHANGELOG.md), очереди и управление обходом. Кандидат для отдельного импортёра в Editor/CLI; не является Unity runtime renderer и не должен становиться обязательной зависимостью Player. Одна страница — отдельный ограниченный режим без обхода ссылок.
- [Playwright .NET](https://github.com/microsoft/playwright-dotnet) — MIT для .NET-обёртки. Может открыть страницу в реальном браузере и помочь с эталонными кадрами, DOM и воспроизводимыми действиями. Браузерные бинарные файлы имеют отдельную поставку/условия; Playwright сам по себе не переносит поведение JavaScript в UI Toolkit.
- [RmlUi](https://github.com/mikke89/RmlUi) — MIT, C++ UI-библиотека с HTML/CSS-подобным форматом. Полезна для изучения layout/рендеринга, но это отдельная UI-система, а не доказанная совместимость произвольного веб-сайта или готовая Unity UI Toolkit-конвертация.
- [Servo](https://github.com/servo/servo) — MPL-2.0, проект встраиваемого web engine. Можно исследовать как потенциальный отдельный browser backend; готовая интеграция с нашим Unity Player, необходимый набор web APIs и стоимость по ресурсам здесь не подтверждены.
- [Spine Unity runtime](https://esotericsoftware.com/spine-unity) — официальный вариант воспроизведения Spine, но его условия отличаются от MIT/Apache. Это **не** универсальная свободная замена браузера; версию 4.2 и права на runtime/ресурсы Chicken Road необходимо проверять отдельно.

## Рекомендуемый порядок проверки

1. Сделать маленькие изолированные spike-проекты для ReactUnity и OneJS: одна страница, реальный JS state/click, style mutation, анимация, input, viewport resize и корректное освобождение ресурсов. Не добавлять оба проекта в обязательные зависимости NeoxiderTools до сравнения.
2. Отдельно сравнить AngleSharp + JS-engine и подходящий web-backend на той же странице. Для web backend проверить границы изоляции, мост к C#, ввод, загрузку ресурсов и рендер в Unity; JS-интерпретатор сам по себе не является изоляцией процесса.
3. Проверить Velora и Chicken Road: HTML/React-обновления, события, CSS, графику, Pixi/WebGL/Spine, реальные состояния и сетевые API. Зафиксировать, что нативно конвертируется, что исполняется в web backend и что пока не поддержано.
4. Измерить одинаковые условия: Unity версии и Player backend, разрешение, железо, first paint, frame time p50/p95/p99, JS/layout/render CPU, GC, native/GPU memory, размер поставки и повторные загрузки. Замеры не подменять заявлениями проектов о производительности.
5. Только после spike выбрать минимальный набор опциональных adapters, зафиксировать лицензии/версии и сохранить поддержку текущих Unity 6.0–6.4 и 6.5+ для базового пакета.

**Предварительный вывод:** ReactUnity и OneJS ближе всего к нативному интерфейсу, AngleSharp/PuerTS/Jint — возможные строительные блоки, а отдельный web-backend может сохранить сложное браузерное поведение. Пока ни один вариант здесь не проверен на обоих пользовательских примерах и не объявляется готовым решением «один к одному».

## Изолированный managed spike

27 октября 2026 выполнен небольшой локальный console fixture на .NET 10.0.9 с AngleSharp 1.8.6, AngleSharp.Css 1.2.2, AngleSharp.Js 1.1.2 и Jint 4.17.0. Итог: **14 проверок PASS, 3 FAIL, exit code 1**. Подтверждены простые JS click/input с изменением DOM, изменение классов и CSSOM, Promise и `setTimeout`; statement и memory limits Jint сработали на отрицательных тестах. `requestAnimationFrame` отсутствовал, поэтому две связанные проверки не прошли; `canvas.getContext('2d')` вернул `null`.

Это измерение только одного синтетического fixture без сети и без Unity: layout, пиксели, CSS animations, WebGL, React, Player, IL2CPP и Chicken Road не проверялись. Хост ожидал завершение callback через тестовый маркер, поэтому синхронную browser-семантику клика результат не доказывает. Временные исходники, versions/hash manifest и логи сохранены в рабочем каталоге этой задачи `D:/Temp/Neoxider-HtmlDemo/spikes/managed-dom`; это не поставляемый компонент пакета.

## Изолированный Windows WebView2 spike

На той же дате отдельно запущен скрытый .NET-хост с установленным WebView2 Runtime 155.0.4283.62 и локальным HTML без сети. Синтетический JS click изменил состояние DOM; Canvas 2D и WebGL2 создали контексты и вернули проверяемые пиксели. Host завершился с кодом 0, его собственные процессы после очистки не остались.

В этом опыте родительское окно и контроллер были скрыты: за 1,2 секунды CSS animation не продвинулась и не было callback от `requestAnimationFrame`. Это не доказывает дефект или плавность видимой Unity-поверхности. Unity Player, plugin gree, физический ввод, сайты Velora/Chicken Road и кроссплатформенность в этом spike не проверялись. Отчёт, локальный fixture и сырые результаты находятся в `D:/Temp/Neoxider-HtmlDemo/spikes/webview2-host`.
